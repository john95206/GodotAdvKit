## 5. 記録すべき知見

- **不確実性は「本実装の前に最小コードで潰す」と安い。** R-13（抽象メソッドの `await`）と
  R-14（ヘッドレスのオーディオ）を 20 行程度の使い捨てスクリプトで先に実測したので、
  設計をやり直す分岐が消えた状態で本実装に入れた。**計画書のリスク表に「最優先」と書いたものは、
  タスク T-01 より前にやるのが正しい。**
- **`Tween.kill()` は `finished` を出さない。** 「終わったら元に戻す」を `tween_callback` に置くと、
  中断されたときだけ適用されない。**中断経路は自然完了経路と必ず別に用意する。**
- **同じプロパティを 2 か所が Tween すると必ず壊れる。** 解は「調停役を置く」ではなく
  **「持ち主を 1 つに決める」**。`modulate.a` は `AdvPortrait`、`ShakeRoot.position` は `shake` 演出、
  というように書き手を一意にすると、台帳は調停だけで済む。
  phase-02 の `AdvScene` が `ShakeRoot.position` を書いていた問題も同じ形だった。
- **「後から始まった方が勝つ」を決めると、中断側の後始末が自動的に決まる。**
  `shake` は原点へ戻す（誰も position を欲しがっていない）、`hide_portrait` は何もしない
  （勝った `show` がノードを使う）。**規約が 1 本あると個別判断が要らなくなる。**
- **テスト用の極小アセットは `.tres` で作るとよい。** コードで `AudioStreamWAV` を組んで
  `ResourceSaver.save()` すれば、6.4KB のテキストファイルになる。バイナリを git に入れずに
  「実際に音が鳴る経路」を検証できる。**実素材が揃う前に音声機能をテストする定石。**
- **ミューテーションテストは安い。** 3 か所を意図的に壊して該当アサーションが落ちることを
  確認するだけで、「全部通った」が「何も検証していない」ではないと言える。**新規テストを書いたら毎回やる。**
- **Windows の Godot は `_console.exe` を使わないと CI にならない。** 無印の `.exe` は
  コンソールに接続せず、出力が出ないうえ**終了コードが実行完了を待たずに 0 を返す**。
  リポジトリに `godot.cmd` のような薄いラッパーを置いて、そこに理由をコメントしておくと事故らない。
