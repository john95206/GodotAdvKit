## 5. 記録すべき知見（document-knowledge 連携）

- **「基底クラスが派生クラスを型注釈で参照できるか」は、エンジンのバージョンごとに実測すべき**。
  Godot 4.5 では解決できたが、仕様書は「できないかもしれない」という前提で回避策を書いていた。
  **回避策を仕様に焼き込む前に、最小再現で測る**。今回は測ったことで、回避を続ける理由が
  「解決できないから」ではなく「設計として基底が派生を知るべきでないから」に変わった。
  同じ結論でも根拠が違うと、後続フェーズの判断が変わる。
- **`.tres` の往復検証は、使い捨てスクリプトで必ずやる。**
  「`ResourceSaver` を呼ばない」という DoD があっても、**検証は別**。
  アドオン外に置いて実行し、終わったら消せばよい。ここを省くと、
  シリアライズが壊れていることに phase-05（セーブ実装）まで気づけない。
- **検証コードの表（§4.9）に「JSON 自体が壊れている場合」が抜けていた。**
  検証コード一覧を設計するときは、**正常系の逸脱だけでなく「入力が前提を満たさない場合」を必ず 1 行入れる**。
  これが無いと、実装者が黙って握り潰すか、勝手にコードを増やすかの二択になる。
- **`--headless` 実行の成否は終了コードで判定する。** stderr にはエンジン由来の
  ERROR 行が出ることがあり（今回はスクリプト型の自己参照によるリーク）、
  「エラー出力があったら失敗」という CI 判定は誤検知する。
- **「同時に走らせられる」と決めたら、「同時に走らせてはいけない組み合わせ」を必ず同時に決める。**
  `parallel_effects` は「複数入れられる」ことだけが仕様化され、
  **同じものを書き換える演出が入ったときどうなるかが未定義**だった。
  並行実行を許す設計には、必ず**排他の単位**が要る。今回は「演出ごとの排他ターゲット」として定義した。
  判定基準を「同じ effect_id か」にしなかったのが要点で、
  `play_se` は 2 本並べても正しく、`show_portrait` + `move_portrait` は同じキャラでも正しい。
  **効くのは ID の重複ではなく、書き換える対象の重複。**
- **検証で防げる範囲と、ランタイムで決着させる範囲を分けて書く。**
  静的検証はステップ内の衝突しか見られない（ステップをまたいだ重なりと、
  ゲーム側が後から登録する拡張演出は見えない）。
  そこは「後から始まった方が勝つ」というランタイム規約で埋める。
  **どちらか一方だけでは穴が残る。**
- **1 行 = 1 レコードのシート表現をネストしたデータへ畳み込む設計では、
  「中間表現の型」を仕様に明記しないと実装が詰まる。**
  今回 `option` に対応する Resource が仕様に無く、`AdvOptionStep` を足す判断が実装者に降りてきた。
  畳み込み前後で配列の要素型を変えない、と決めるなら中間型は必ず要る。
